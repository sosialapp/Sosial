## Auth keys
- Gateway: Envoy (Lua `apikey` check). Protected routes require the `apikey` header — including `/auth/v1/`, `/rest/v1/*`, `/storage/v1/*`, `/graphql/v1`, `/pg/*`. `/rest/v1/` (bare) is the OpenAPI route, service_role only. **Both** the anon and service-role keys are accepted as `apikey` (verified 200), so the worker's `apikey: SERVICE_ROLE_KEY` headers work unchanged.
- Legacy symmetric keys (`ANON_KEY` / `SERVICE_ROLE_KEY`, HS256) remain valid.
- Asymmetric ES256 pair enabled (`JWT_KEYS` / `JWT_JWKS`) + opaque `sb_publishable_` / `sb_secret_` keys.
- Generated by `docker/utils/generate-keys.sh` and `docker/utils/add-new-auth-keys.sh` — never commit `.env`; regenerate if leaked.

## Compose
- Supabase stack: Envoy :8000, GoTrue, PostgREST, Storage, edge-runtime, Supavisor (`pooler`), Postgres :5432, postgres-meta
- Edge functions: repo `supabase/functions/*` (43 fn + `_shared`) copied into `docker/volumes/functions/`; the `functions` service uses `env_file: .env`; **`FUNCTIONS_VERIFY_JWT=false`** — the runtime gate is global in this rev, and every function self-authorizes (Bearer → `/auth/v1/user`, or `DORMANCY_TOKEN` for the crons), so the gate must stay off (also required by `media`'s public blog-image action).
- `infra/docker-compose.services.yml`: web, worker, photo-host (:3000 loopback), uptime-kuma (:3001 loopback), plus monitoring — beszel (:8090 loopback, hub) + beszel-agent (`network_mode: host`, local unix socket) + dozzle (:8080 loopback, logs). Monitoring UIs are loopback-only and meant to sit behind Cloudflare Access (`metrics.` / `logs.` subdomains).
- **`sosial-web`** (Next.js dashboard) — built from `../apps/web` with Next `output: 'standalone'`, published on `127.0.0.1:3002` only. `NEXT_PUBLIC_*` are **build args** (Next inlines them), so changing the Supabase URL/anon key/site URL requires `build web`, not just `up -d`. Runtime secrets (`SUPABASE_SERVICE_ROLE_KEY`, Stripe, Resend) come from `.env`. `sharp` needs a Linux/glibc build host; never build this image from Windows/macOS.
- `sosial-web` + `sosial-worker` + `sosial-photo-host` images are built on the box (repo shipped as a tar, not cloned); photo-host + uptime-kuma run now, **web is built and healthy on `127.0.0.1:3002` but stays loopback-only until the DNS cutover** (Vercel keeps serving until then), worker runs the p115 auto-reply build.
- Sosial services join the Supabase Docker network **`supabase_default`** and reach the gateway as `api-gw:8000` (no host-published port needed).
- **Docker publishing bypasses UFW.** Supabase's `:8000/:5432/:6543` binds were changed to `127.0.0.1` in `docker-compose.yml` (backup `docker-compose.yml.bak-ports`) — verified closed from the internet. Never bind a Supabase port to `0.0.0.0`.
- Log caps on every service (no disk-eating json logs)
- `sosial-web` has `mem_limit: 3g`; it restarts if it climbs past that
- Envoy `rest` health check in `/opt/sosial/supabase/docker/volumes/api/envoy/cds.yaml` (server only, not in this repo) is `/__health` with `expected_statuses` 200 to 404. PostgREST answers that 404 from its schema cache in about 5 ms, and a 503 still counts as unhealthy. The upstream `/` built the 288 KB OpenAPI document every 5 s. Re-apply this after any Supabase compose update.

## Ingress (Caddy)
- `caddy` (apt, cloudsmith repo, **≥ 2.11** — `tls force_automate` is 2.11+) with a Cloudflare **Origin Certificate** covering `sosial.app` + `*.sosial.app` at `/etc/caddy/certs/origin.{pem,key}` (key `600 caddy:caddy`). The canonical config is `infra/caddy/Caddyfile`; `/etc/caddy/Caddyfile` is root-owned so it is installed by hand (see below).
- Sites: `db.sosial.app` → `127.0.0.1:8000` (Supabase gateway), `status.sosial.app` → `127.0.0.1:3001` (Uptime Kuma), `sosial.app` + `www.sosial.app` → `127.0.0.1:3002` (web app), `photos.sosial.app` → `127.0.0.1:3000` (TikTok photo host). `encode zstd gzip` on everything but `www` (a 301 to the apex). Caddy listens `:80`/`:443`; nothing else is public.
- **`photos` must not use the origin cert.** That host is grey-cloud/DNS-only (TikTok rejects 3xx redirects, so it can't go through the Cloudflare proxy) and therefore has to present a publicly-trusted **Let's Encrypt** cert. The origin cert is a wildcard, so it *also* matches `photos`, and a manually-loaded cert wins over ACME — the block must opt out with **`tls force_automate`**. Without it Caddy terminates with the (untrusted) origin cert and every client sees `unable to verify the first certificate` (chain depth 1, verify code 21); Uptime Kuma goes red and TikTok can't download uploads.
- In the adapted JSON the other blocks load the origin cert tagged `cert0` and pin their SNIs to it (`certificate_selection.any_tag: ["cert0"]`); the `photos` policy has no such pin and appears in `tls.certificates.automate`, so it can only be served by Caddy-managed (ACME) certs.
- `www` is redirected to the apex by Caddy itself; `docs.sosial.app` is rewritten to `/docs/*` by the app middleware (`docs.` is not a separate site block).
- After editing the Caddyfile: `sudo cp infra/caddy/Caddyfile /etc/caddy/Caddyfile && sudo caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy` (`systemctl enable --now` does **not** reload a running unit).
- The admin API on `127.0.0.1:2019` is unauthenticated (loopback only) and accepts a full config: `curl -X POST http://localhost:2019/load -H 'Content-Type: text/caddyfile' --data-binary @Caddyfile`. Useful for a fast fix, but it is **in-memory only** — the next `reload`/restart reverts to `/etc/caddy/Caddyfile`, so always persist the file too.

## Web self-host runbook (Vercel → VPS)

The web app is a normal Next.js server (API routes, server components, middleware, ISR, `sharp` image watermarking), so it runs as a container behind Caddy; no static export, no Vercel-specific code.

1. **Env** — in `/opt/sosial/infra/.env`, set `NEXT_PUBLIC_SUPABASE_URL=https://db.sosial.app`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (self-hosted anon key), `NEXT_PUBLIC_SITE_URL=https://sosial.app`. `SUPABASE_SERVICE_ROLE_KEY` comes from `WORKER_SERVICE_ROLE_KEY`. **Still missing on the box (copy from Vercel before/after cutover): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`** — billing checkout and the signup marketing opt-in stay disabled without them. These are runtime-only, so `docker compose … up -d web` is enough; no rebuild.
2. **Build on the box** (Linux/glibc, for `sharp`):
   ```bash
   cd /opt/sosial/infra
   docker compose -f docker-compose.services.yml build web
   docker compose -f docker-compose.services.yml up -d web
   docker compose -f docker-compose.services.yml logs --tail=100 web
   ```
3. **Smoke test before DNS** (container is loopback-only):
   ```bash
   curl -fsS http://127.0.0.1:3002/api/health
   curl -sI -H 'Host: sosial.app' http://127.0.0.1:3002/ | head -5
   ```
   `NEXT_PUBLIC_SITE_URL` is baked in at build time; to test on a temporary hostname, build with that hostname and add it to Supabase Auth → URL Configuration first.
4. **TLS** — reissue the Cloudflare Origin Certificate with `sosial.app`, `www.sosial.app`, `docs.sosial.app` added to the existing `db.` / `status.` SANs, then add the Caddy block above and `sudo systemctl restart caddy`.
5. **DNS** — in Cloudflare, snapshot the current `sosial.app` / `www` / `docs` records (they point at Vercel), then change them to the VPS IP, proxied. `docs.` is optional but keeps the docs on the same deployment, which is how middleware already routes it.
6. **Post-cutover checks** — `/` and the marketing pages, `/login` + email/Google callback, `/dashboard`, a signed-in API call, `/api/billing/webhook` (Stripe dashboard delivery), `/opengraph-image` + `/og?t=test`, `https://docs.sosial.app/api`, and `www.sosial.app` → apex 308.
7. **Rollback** — point the three Cloudflare records back at Vercel; the Vercel project stays deployed until the self-hosted app has run cleanly for a week.

Updates are `git`/tar + `docker compose build web && up -d web`; the standalone image replaces cleanly and `web-next-cache` keeps the ISR cache.

Self-hosted web gotchas:
- `.dockerignore` keeps `.env*` out of the image — secrets arrive as runtime env, never baked in.
- The image must be built on Linux x86_64. `npm ci` on Windows/macOS installs the wrong `sharp` binary and the container dies on the watermark route.
- Marketing pages use `revalidate = 300` and a filesystem cache; `/app/.next/cache` is a volume so restarts do not cold-start every page.
- The web container reaches Supabase through the public `https://db.sosial.app` (it needs to work from the browser too). Do not swap `NEXT_PUBLIC_SUPABASE_URL` for `http://api-gw:8000`: signed storage URLs would then point at an unreachable Docker hostname.

## Gotchas
- `infra/backup.sh` runs from root cron (`/etc/cron.d/sosial-backup`), so it must stay executable with LF endings. Ship it with `git archive`; a Windows tar left it CRLF and mode 664, which stopped backups on 2026-11-03. Never test it with a different `BACKUP_DIR` while R2 sync is on: `aws s3 sync --delete` would remove every off-site backup not in that folder.

- Postgres data is a **bind mount** (`docker/volumes/db/data`), not a named volume. `docker compose down -v` does NOT clear it. After changing `POSTGRES_PASSWORD`, delete that dir before `up`, or roles keep the old password and every service crash-loops with `password authentication failed`.

- Auth schema drift (self-hosted `gotrue:v2.196.0` vs cloud, newer): cloud-only tables `mfa_recovery_code_sets`, `mfa_recovery_codes`, `scim_tokens`, `scim_users` (all 0 rows) and `auth.one_time_tokens.expires_at` column. Exclude these from data restore — no real data affected (1 transient one-time token dropped).

- Cloud project is restricted (`exceed_egress_quota`); every Storage request returns **402** (S3 and REST alike). No payment needed: the free-plan restriction **auto-lifts at the next billing-cycle reset** (date on dashboard → Upcoming Invoice), or instantly on upgrade / spend-cap change. Keep the cloud org alive until the few remaining objects are copied.
- Media already lives on R2 (`sosial-media`, prefix `post-media/`): **all 28 `media_assets` rows are `storage_backend='r2'`** and present there. Legacy Supabase objects that are actually referenced: the 5 post-media (already in R2) and **exactly one blog cover, `blog-media/covers/1790319056534-76q9p90v3x8.png`**. The other 40 post-media are orphans, the 2 `avatars` and 21 blog-media match nothing. Only thing to fetch once the quota resets = that single PNG.

## Restore (disaster procedure)
1. Fresh box + base install (Stage 1 commands)
2. `aws s3 cp s3://sosial-backups/sosial/<latest-pg>.sql.gz - | gunzip | psql` (or `supabase db reset` + data restore per runbook)
3. Re-copy buckets from R2 (`aws s3 sync s3://sosial-media/post-media/ ...`)
4. Re-inject 34 secrets, `docker compose up -d`, run E2E checklist
5. Monthly restore TEST (untested backups aren't backups)
